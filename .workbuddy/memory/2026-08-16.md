## 修复启动崩溃：conda Windows openssl 钩子 SSL_CERT_FILE 坏路径

- 现象：python src/app.py 启动崩溃，httpx create_ssl_context 读 SSL_CERT_FILE 报 FileNotFoundError
- 根因：kbqa/chaos_seg 环境的 etc/conda/activate.d/openssl_activate.sh（旧版 conda 生成）把 SSL_CERT_FILE 设为 ${CONDA_PREFIX}/ssl/cacert.pem（小写 ssl），Windows 版 conda 实际在 Library/ssl/cacert.pem → Git Bash 激活后变量指向不存在的文件（.bat/.ps1 钩子路径正确，CMD/PowerShell 不受影响）
- 修复：① 两个环境的 openssl_activate.sh 改路径 + -f 存在性判断（文件不存在则不设变量）② app.py 顶部加防御：SSL_CERT_FILE/REQUESTS_CA_BUNDLE/CURL_CA_BUNDLE 指向不存在文件则清除并告警
- 验证：模拟激活 FILE_OK；预置坏变量 import app → 清除生效 + langchain_ollama 导入成功；py_compile 通过
- 运维：用户需 conda deactivate && conda activate kbqa（或新开终端）让新钩子生效；app.py 防御可兜底旧终端

## Trace 方案评估（参考 Obsidian 20260815 技术 Trace模块引入与行业实践）

- 结论：一期自建轻量 Trace（SDK 嵌入 Harness 埋点 + LLMFactory 代理层，SQLite 存储，task_id=trace_id，数据结构按 OTel 语义设计）；二期触发式上 Langfuse/Phoenix 自托管
- 排除 LangSmith/W&B（SaaS 数据出境）；框架集成不可行（自研 Harness 主循环，LangChain 埋点覆盖不到决策节点）
- 评估报告：docs/trace_evaluation.md；决策已记录 docs/business_knowledge.md；待办含 TraceCollector/TraceProxy/前端时间线落地

## Trace 一期方案落地

- 新增 `code/src/agent_trace.py`：TraceEvent（OTel 语义）+ TraceCollector（daemon 线程异步批量写 SQLite data/agent_traces.db，独立库文件避免与 agent_tasks.db 写锁竞争）+ trace_span 上下文管理器 + ContextVar 绑定当前 trace
- LLM 代理层采用 **LangChain callbacks 钩子**而非对象包装（RAG 链是 LCEL 管道，包装会破坏 Runnable 协议）：llm_factory 三个构造方法挂 _trace_callbacks，记录模型/token/耗时/prompt长度；非 Agent 路径归属 adhoc
- Harness 埋点：plan_create/plan_revise/subtask_schedule/tool_call（预占位时间戳计时）/idempotent_block/resume/task_end；run_loop 入口 set_current_trace(task_id)
- app.py：lifespan 最先初始化 TraceCollector（保证 RAG 链 LLM 创建即挂回调）、停机 flush；新增 GET /api/agent/tasks/{task_id}/trace（查询前 flush）
- 前端：Agent 面板"调用链 Trace 时间线"（偏移时间轴 + OK/失败 + tokens/模型摘要）
- 冒烟测试 6 场景 23 项全过；隔离 venv 装了 langchain-core（清华镜像，pypi 超时）
- 已知取舍：低 QPS 全量上报不采样；Embedding 调用未追踪（callbacks 不覆盖 embeddings）
